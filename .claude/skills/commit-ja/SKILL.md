# Conventional Commit (日本語)

変更内容を分析して、ファイル単位を基本に適切な粒度へ分割し、Conventional Commits形式の日本語コミットメッセージを生成して、ユーザー確認後にコミットします。

## 使用方法

```
/commit-ja
```

## 実行手順

### 1. Git ステータスの確認

```
`!scripts/get-git-status.sh`
```

このスクリプトは以下を出力します：
- ステージングされた変更
- ステージングされていない変更
- 未追跡ファイル
- ステージング済み・未ステージ変更のdiff

出力から `STAGED`、`UNSTAGED`、`UNTRACKED` の値を確認します。

### 2. コミット分割方針の決定

- `STAGED=1` の場合: ステージング済み変更も最終的なコミット単位とはみなさず、確認済み候補として扱う。staged diff と未ステージ変更を合わせて再分析し、必要ならコミット計画で分割する
- `STAGED=0` かつ `UNSTAGED=1` の場合: `git add .` は使わず、差分をファイル単位で分析してコミット計画を作る
- `UNTRACKED=1` の場合: 未追跡ファイルの内容を必要に応じて `Read` や `git diff --no-index /dev/null <path>` で確認し、コミット対象に含めるかをコミット計画で明示して確認する
- `STAGED=0`、`UNSTAGED=0`、`UNTRACKED=0` の場合: コミットする変更がないことを報告して終了

以下の基準でコミット計画を作成します：

- 1ファイルだけで意味が完結する変更は、原則としてそのファイル単位で1コミット
- 同じ目的の変更で、実装ファイルとテスト、型定義、設定、lockfileなどが密接に対応する場合は1コミットにまとめる
- Conventional Commits の type や scope が異なる変更は別コミットに分ける
- 無関係な修正、整形、ドキュメント更新、依存関係更新は混ぜない
- 同じファイル内に複数の無関係な変更がある場合は、ファイル単位では分けられないことをユーザーに伝え、必要なら部分ステージング方針を確認する
- untracked ファイルは、コミット対象に含めてよいかユーザー確認に明記する

### 3. 変更内容の分析

各コミット候補ごとに diff の内容から以下を判断します：

#### Conventional Commits のタイプ

- **feat**: 新機能の追加
- **fix**: バグ修正
- **docs**: ドキュメントのみの変更
- **style**: コードの意味に影響しない変更（空白、フォーマット等）
- **refactor**: バグ修正でも機能追加でもないコード変更
- **test**: テストの追加・修正
- **chore**: ビルドプロセスや補助ツールの変更

#### スコープの判定

変更されたファイルのパスや内容から、スコープを推測します：
- `src/auth/` → `auth`
- `src/components/Button.tsx` → `button` または `components`
- パッケージ管理 → `deps`
- CI/CD関連 → `ci`
- 複数領域にまたがる場合は省略

### 4. コミット計画とメッセージの生成

コミット候補ごとに対象ファイルとメッセージを生成します。

```
1. 対象: src/auth/login.ts, src/auth/login.test.ts
   メッセージ:
   feat(auth): ログイン処理を追加

2. 対象: README.md
   メッセージ:
   docs: セットアップ手順を更新
```

メッセージは以下の形式で生成します：

```
<type>(<scope>): <description>

<body>
```

**例:**
```
feat(auth): ログイン機能を追加

- JWT認証を実装
- ログインフォームコンポーネントを作成
- 認証ミドルウェアを追加
```

```
fix(button): クリック時のイベント伝播を修正
```

```
refactor: コード構造を整理
```

**ルール:**
- description は日本語で簡潔に（50文字以内推奨）
- body は必要に応じて詳細を箇条書きで記載
- Breaking Change がある場合は body に `BREAKING CHANGE:` を含める

### 5. ユーザー確認

生成したコミット計画と各コミットメッセージをユーザーに提示し、以下を確認します：

```
以下の計画でコミットしますか？

1. feat(auth): ログイン機能を追加
   対象:
   - src/auth/login.ts
   - src/auth/login.test.ts

2. docs: READMEのセットアップ手順を更新
   対象:
   - README.md

よろしければ「はい」と答えてください。
分割単位やメッセージを修正したい場合は修正内容をお知らせください。
```

### 6. コミット実行

ユーザーが承認したら、計画した順番で対象ファイルだけをステージしてコミットします。

```bash
git add -- path/to/file1 path/to/file2
`!scripts/git-commit.sh "コミットメッセージ"`
```

複数コミットの場合は、各コミットごとに以下を繰り返します：

1. `git status --short` で現在の状態を確認
2. 既存のステージングに今回の対象外ファイルが含まれている場合は、承認済みのコミット計画に沿って `git restore --staged -- <path>` で対象外だけを外す
3. 対象ファイルだけを `git add -- <path>` でステージ
4. `git diff --cached --name-status` でステージ対象が計画通りか確認。対象外のファイルが含まれている場合はコミットせず、index を修正するか、判断できない場合は状況を報告してユーザーに確認する
5. スクリプトを使ってコミット

```bash
`!scripts/git-commit.sh "コミットメッセージ"`
```

**重要**: このスクリプトは Claude Code の署名を含めずにコミットします。

**禁止**: 承認済みのコミット計画なしに `git add .`、`git add -A`、全ファイル対象のステージングを実行しないでください。

### 7. 結果の報告

コミットが成功したら、作成した各コミットのハッシュ、メッセージ、対象ファイルを報告します。

## コンテキスト最適化

このスキルは以下の方針でコンテキストを最適化しています：
- Git コマンドの実行は `scripts/` ディレクトリのスクリプトに分離
- SKILL.md には変更内容の分析とメッセージ生成のロジックのみ記述
- ユーザーとの対話は SKILL.md で処理
- `` `!command` `` 構文でスクリプト出力を動的に注入

## 注意事項

- このスキルはClaude Codeの署名を含めません
- ステージングされていない変更がある場合でも、一括ステージングは提案しません
- コミット前に必ずユーザーに確認します
- ファイル単位を基本に、意味のある変更単位へ分割します
- Conventional Commits の形式に従った日本語メッセージを生成します
- Breaking Change がある場合は必ず body に記載します
